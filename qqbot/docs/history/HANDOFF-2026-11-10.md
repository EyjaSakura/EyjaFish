## 结构

```
lib/
  bridge.js            # 仅剩编排、适配、少量业务分支
  core/                # 与 QQ 无关的纯逻辑：路由、注入、会话、handoff、锁、映射
  services/            # 有副作用但可注入的用例：清理、轮询、注册、命令、媒体
  tools/               # 工具定义/注册：face、web、各类 qq_* 工具
  features/            # 可插拔功能（feature-loader 加载）
  *.js                 # 历史模块（ops/engage/acl/...），多数已有测试
```

features 只依赖 `lib/sdk/index.js`；services 可被单测直接 import；bridge 只做接线。

## 主要剩余缺口

### 1. bridge 仍然 5.5k 行

最大块：

| 位置 | 约 | 性质 |
|---|---|---|
| `#onQqMessageInner` | 102 行 | 主要是 `#bridgeApi({...})` 映射表 |
| `#installSession` | 76 行 | 同上 |
| 各类 `#handleXxxCommand` | 30–40 行/个 | 同上 |

这些行大多不是“业务逻辑”，而是**私有方法到功能 ctx 的逐项映射**。
下一步不是继续一行行搬，而是做一次结构性重构：

- 方案 A：把功能 ctx 统一为“按需传入 bridge 公共接口”，删掉每个方法的映射表；
- 方案 B：把 `#bridgeApi` 的构造收敛到一个集中映射，只构建一次；
- 方案 C：按领域拆成 `SessionRuntime` / `CommandRuntime` / `MediaRuntime` 组合类。

做完这一步，bridge 才可能从 5.5k 降到 3k 以下。

### 2. bridge 覆盖率未纳入

原因：`bridge.js` 直接 import 宿主包（`@deepseek-ai/dsh-*`），单测进程无法加载。
可行路径：

1. 给 bridge 加最小依赖注入边界（构造参数注入宿主 API），再用 fake 宿主加载；
2. 或者用子进程 + 真实宿主做集成测试，只统计调用到的分支；
3. 短期可先把 bridge 的**纯函数**继续抽到 core，覆盖率统计自然覆盖这些分支。

目前 bridge 只参与 typecheck / no-undef / unused / 行数门禁，不参与 coverage。

### 3. 真实 agent e2e

已有 `test/agent-loop-e2e.test.mjs`：handoff → fake followup → replyTo → 真实 OneBotServer WS。
它验证了桥接的回路，但**不是真实 DSH agent 回合**。

要再往前一步，需要：

- 起一个真实 `agentCtx` / `agents.create` 的宿主进程；
- 用测试 QQ 号或注入帧触发一轮真实模型回合；
- 断言回复文本/工具调用，而不是只断言 WS 帧。

这会引入模型调用成本与非确定性，建议单独做 nightly，不进每次 CI。

## 不要做的事

- 不要为了降行数把业务逻辑塞回 bridge；
- 不要用 `@ts-nocheck` 换 typecheck 绿；
- 不要把 coverage 门禁下调来“通过”；
- 新增功能放 `features/` 或 `services/`，bridge 只加接线。
